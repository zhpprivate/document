# 部门研发协作与交付改进方案

> 适用：现有总监、架构师、5 名产品、前后端及移动端开发、测试团队。统筹人及授权落实后启动 60 天试点，持续能力缺口按评估补充；下述时间与容量比例为试点初值。

**核心安排：**优先由通过试任的现有产品经理牵头一个版本的完整交付，现有组长承诺并落实各组任务，架构师裁定跨系统技术事项，测试组长统筹质量验证；部门日常资源与交付统筹由**交付统筹人（待定）**承担，总监保留方向、授权与重大审批。

## 一、人员与职责安排

| 现有人员 | 具体承担的工作 | 权限与边界 |
|---|---|---|
| **总监：方向与重大审批** | 确定平台方向、预算和授权范围，审批重大资源投入及管理规则。 | 按约定审批窗口处理重大事项，日常排期、协调、试任复核由交付统筹人负责。 |
| **部门交付统筹人：人选待定** | 部门需求排序、跨版本资源平衡、试任与交接；每周主持一次 30 分钟优先级与风险会。 | 公司明确人选并书面授权后，在已批目标与容量内决定日常取舍，核查排期依据；超出授权的事项报重大审批。 |
| **每个系统现有产品经理** | 持续维护所负责系统的需求、业务规则、验收标准和优化清单；优先试任对应版本的交付牵头人。 | 组织协作、维护整体计划、协调验收；范围和日期变化按规则确认，不自行替开发承诺工期。 |
| **现有后端组长** | 兼任本组系统技术与实施负责人，落实后端及分配到本组的前端、移动端任务。 | 校核估算、安排组内任务、承诺依赖日期、组织代码评审和发布；前端专业问题由前端牵头人支持。 |
| **现有架构师 1 人** | 跨系统技术决策、质量标准、关键实现检查、平台共性能力与技术债治理。 | 在批准的目标和容量内裁定技术方案、要求整改、按既定门槛阻断发布；资源和日常业务取舍交交付统筹人，重大变更按授权报批。 |
| **现有测试组长** | 分配各版本测试容量，统筹回归、风险覆盖和发布质量结论。 | 每版指定 1 名现有固定系统测试作为测试对接人；不满足既定质量门槛可阻断发布。 |
| **现有 6 名前端中的 1 人** | 兼任前端规范与公共组件牵头人。 | 第 1 周由交付统筹人会同架构师，依据组件维护及代码评审经验确定人选，并减少其功能任务；具体评审由前端成员分担。 |

**交付统筹人的空缺安排：**人选暂不指定，不默认由总监、架构师或某位组长兼任。候选须具备跨系统交付经验和持续投入时间，可从内部调入或招聘后试任。部门统筹负责跨版本资源与例外事项，各版本牵头人仍跟踪本版本任务。

**空缺期间：**已有具名负责人、资源已确认的工作继续执行；需求澄清与独立交付可以推进。新的跨系统交付承诺须待统筹人及必要版本负责人落实；需要其裁决的冲突登记待处理，受影响工作暂缓，不将空缺职责默认转交总监。60 天试点从统筹人及授权落实后计时。

## 二、交付负责人优先从现有产品中选任

| 版本类型 | 由谁牵头 | 如何确定 |
|---|---|---|
| 单系统版本 | **优先选择当前负责该系统的产品经理** | 沿用现有业务归属，核实交付管理能力及容量后试任。 |
| 跨系统业务版本 | **优先选择负责主业务结果及验收的产品经理** | 交付统筹人在排期前确认试任；其他产品协助规则与验收，组长分别承诺实施任务。 |
| 无明确主业务归属的联合版本 | **交付统筹人从参与版本的现有产品中指定 1 人** | 先判断是否可以拆成独立交付；确需统一上线时，按业务理解、协调经验和可用容量选定，确定后再承诺日期。 |

**选任依据：**产品掌握需求与验收目标；具备计划和协调能力、且有实际容量时优先牵头。技术判断和组内安排分别由架构师、组长承担。

**授权与减负同时落实：**公司批准交付协调权限，交付统筹人落实到牵头产品，支持其召集跨组协作、要求任务更新、提出范围／日期调整并升级冲突；各组接受协调、提供承诺。同一产品经理试点期最多牵头 **1 个跨系统版本**，初始预留约 **30% 工作时间**用于交付管理，相应减少其他需求编写和评审任务。两轮后按实际负荷校准；容量不足时调整范围或顺序，日常资源取舍由交付统筹人在授权内处理。

**示例：**A 发起、B 处理、C 回传的业务，优先由负责最终验收的 A 产品牵头，各组分别承诺任务；无人满足条件时，按第六节补位。

## 三、一个版本怎样推进

| 环节 | 谁做、做到什么程度 |
|---|---|
| 需求准备 | 牵头产品每周滚动澄清，写清业务目标、范围、验收示例、接口依赖。已就绪且可独立交付的需求先排期，其他项继续补充。 |
| 联合排期 | 开发与测试拆分估算，组长校核；牵头产品汇总依赖、联调、修复及回归窗口。共享前端、移动端、测试纳入一张容量表，交付统筹人核查并在授权内确认排期。 |
| 执行跟踪 | 牵头产品维护唯一版本看板：任务、实施人、依赖人、承诺日、状态、阻塞。每天安排不超过 15 分钟同步，组长对本组状态负责。 |
| 变更与升级 | 延期风险当天记录；阻塞超过 1 个工作日由牵头产品组织解决。技术争议交架构师，资源／优先级冲突交交付统筹人，建议下一工作日给出处理结论；超出授权时明确待审批范围及受影响任务。插单须记录替换项及新日期。 |
| 验证与发布 | 开发完成自测与同行评审，测试形成验证结论；牵头产品组织业务方验收。系统技术负责人执行发布、回滚准备与上线验证；牵头产品核对完整交付清单后结项。 |
| 演示与改进 | 每两周演示成果并复盘，产品与组长选择 1 项业务或质量改进进入下轮容量表；同类前端问题由前端牵头人组织组件、规范或测试改进。 |

小批量推进、共享工作可见及按容量限制并行，可参考 [DORA 的在制品管理建议](https://dora.dev/capabilities/wip-limits/)。

## 四、架构师必须交付的具体成果

由总监在试点开始前书面确认下列技术权限；组长落实技术决定，架构师核查关键实施结果。

| 工作 | 决策及可检查成果 |
|---|---|
| 跨系统技术方案 | 确定接口契约、数据归属、兼容性及一致性处理；输出简短决策单：选定方案、理由、实施人、验证方法、完成日期。 |
| 技术争议处理 | 信息齐备后建议 2 个工作日内作决定；信息不足时列补充项、责任人和再决策日期。超出已批容量的方案须先由总监确认投入。 |
| 实现与风险检查 | 对跨系统或高风险需求设置设计、联调和发布检查点；留存验证记录，偏差形成具名整改任务并确认关闭。普通组内方案由现有组长决定。 |
| 发布技术门槛 | 与测试组长拟定标准，经总监批准执行。核心流程不可用、数据错误等严重问题未关闭不得发布；一般遗留风险由获授权的交付统筹人书面接受，重大风险报总监审批，均确定补救人和期限。 |
| 平台与共性治理 | 与牵头产品选择 1 项已批准的共性能力或技术债，完成关键设计／原型并组织实际落地，以使用效果验证；相关工作占用明确的开发和测试容量。 |

架构师固定参与上述技术决策、重大故障复盘与平台技术会议；普通需求、进度同步由牵头产品和组长组织。每个周期评价其约定技术成果、关键检查和治理效果；版本整体质量用于团队改进，个人评价结合职责、实际权限和可控影响。

## 五、绩效按约定与证据执行

绩效标准事先记录、可核验，并匹配资源条件；定性评价同样明确观察依据与评价人，参考 [OPM 的绩效标准设计原则](https://www.opm.gov/policy-data-oversight/performance-management/reference-materials/articles/developing-performance-standards/)。

- **期初：**每人约定 3–5 项主要成果，写清验收证据、截止日、依赖资源、权重及评分档位。牵头产品考核交付计划、依赖管理、预警、业务验收及约定结果；架构师考核第四节成果；组长考核本组实施、评审及改进，测试考核约定覆盖与验证结果。
- **期中：**每两周反馈一次；资源、范围与日期变化同步修订受影响目标，保留原记录。协作、复用与改进成果纳入正向评价。
- **期末：**评分对应事前条款、事实、影响、个人可控性与档位；任何调分均留依据。质量事件区分需求、设计、实现、验证和管理取舍，不按缺陷总数平均扣分，不对同一行为重复扣分。
- **复核：**员工可在建议 3 个工作日内提出异议，由相关产品、组长与测试核实事实；涉及评分人本人决策的争议，由公司指定的上级或独立复核人处理。

新规则先模拟评分一轮，不直接用于奖金调整；校准后下周期正式执行。

## 六、试点中如何调整人员

**先调整任务与职责，再决定是否需要调整岗位。** 交付统筹人在授权内安排版本负责人、跨组调配及项目职责复核；组长管理本组开发，测试组长管理测试。正式岗位任免和绩效处理按公司权限办理。专业能力依据工作样例和同行评审核验，架构师本人的技术能力评审由公司其他资深技术人员或经批准的专项专家参与。

**交付统筹人到位后公布试任名单，运行两周后复核。** 每名负责人写清范围、容量、验收标准、复核日，并从参与人员中指定一名具备接手条件的备份。交付试任至少核验：能形成整体计划、获得依赖承诺、及时预警并组织处理。备份缺位须登记，收窄其可承诺的交付范围。试任是项目职责安排，复核窗口不等同于正式人事处理期限。

| 运行中出现的情况 | 具体调整与复核 |
|---|---|
| 授权不清、任务冲突或负荷过满 | 由对应主管澄清职责；跨组冲突由交付统筹人在授权内调整优先级、减少任务或补容量，更新计划后再评价履行情况。 |
| 某项技能暂不能满足要求 | 主管指定有相应经验的导师，约定 2–4 周的辅导目标、练习任务与验收证据，每周反馈。关键风险先由合格人员承接，不能以培训代替必要的交付保障。 |
| 专业工作胜任，但不适合跨组协调 | 经试任证据确认后，改由另一名合格产品牵头；原产品保留需求与业务验收职责。组长也可调整协调职责、保留专业实施工作，不把负责人角色作为唯一发展路径。 |
| 职责、资源和期限已明确，约定的协作行为仍持续未落实 | 主管核实具体任务、响应记录及员工说明，明确改进项与复核日；支持后仍重复发生，由交付统筹人在授权内调整项目分工，必要时进入公司正式绩效／人事程序。合理异议、如实报告风险及已确认的容量冲突单独处理。 |
| 辅导后仍不能满足该职责要求 | 按期初标准复核，由交付统筹人在授权内收窄项目职责或换版本负责人，安排匹配其已验证能力的工作；同时根据持续工作量提出内部调入或招聘申请，不无限期延长代岗。 |

**没有合适交付负责人时，按顺序补位：**主责产品 → 其他合格产品（重分系统、同步减负）→ 熟悉业务且具协调能力的现有组长临时代任（减少编码任务，原产品负责业务验收）。仍无人承接时，版本负责人标为**待定**，由交付统筹人申请公司内部调入或招聘，暂缓该版本的上线承诺；交付统筹人自身尚未到位时，按本方案的空缺规则执行。关键技术职责无人胜任时，先申请公司技术支持或专项评审，暂停相应高风险变更。

**更换负责人须有交接：**交付统筹人确认交接生效时间，原、新负责人移交范围、计划、依赖、风险、决策及未完成项；相关组重新确认资源与日期。建议预留 1–2 个工作日，关键风险立即由临时负责人接管。生效后只保留一名交付负责人，原承诺和变更记录保留，绩效按实际承担期间和可控行为评价。岗位、薪酬或劳动关系变更另由公司授权的人事程序办理。

上述机制以明确预期、提供资源与支持、持续反馈和改进为基础，参考 [CIPD 的绩效管理原则](https://www.cipd.org/en/knowledge/factsheets/performance-factsheet/)。

## 七、60 天试点及平台目标

| 时间 | 现有人员与交付物 |
|---|---|
| 启动前 | 公司明确交付统筹人及授权，总监确认方向与重大审批边界；未落实时先澄清需求，暂缓新的跨系统交付承诺。 |
| 到位后第 1 周 | 交付统筹人选定 1 个跨系统需求，填写参与人员**实际姓名**，确认容量、备份、两周复核日期与试行规则。 |
| 第 2–4 周 | 复核试任并执行减负、辅导或交接；牵头人完成一批可验收交付，架构师和测试提供验证记录。 |
| 第 5–8 周 | 交付统筹人复核人员适配、辅导及补位，比较交付与质量数据，形成推广建议；重大资源投入报总监审批。 |

平台方向由总监向全员说明。**由负责拟对外输出核心业务的现有产品经理牵头平台验证，减少其同期其他任务**；牵头产品联合公司业务／销售人员安排访谈，总监协调必要的高层资源；产品访谈约 3–5 家客户，确认共性需求、付费意愿、实施与支持成本；架构师评估配置、隔离、部署升级等技术能力。60 天内形成最小可售范围、成本和继续／调整／暂停建议。
