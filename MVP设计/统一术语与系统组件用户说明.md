# 统一术语与系统组件用户说明（MVP最终版）

| 文档属性 | 内容 |
| --- | --- |
| 版本 | V1.1 |
| 日期 | 2026年8月25日 |
| 适用范围 | MVP需求、原型、接口、数据库、测试和业务培训 |

## 一、统一口径

1. 委托运输并向我方支付费用的企业统一称为“委托厂商”。
2. 系统一级服务类型只有“整车运输服务”和“开送服务”。板车运输是整车运输服务的执行方式；单车、编组和背载是开送服务的执行方式。
3. “运输需求”是厂商的一条原始交付要求；“业务订单”是系统中承载服务类型、交付标的和结算关联的中性业务单据。
4. 现有TMS的“内部运单”只作为历史映射，不再用于制造虚拟货物或虚拟车牌；“运输任务”表示一次可执行安排，“执行单元”表示最小真实履约单元。
5. 客户应收和履约应付必须分开，不能用同一个“运费”字段表示收入和成本。
6. 第一期只有内部运输运营后台，没有司机端、承运商门户或委托厂商门户。

## 二、业务分类术语

| 统一术语 | 定义 |
| --- | --- |
| 整车运输服务 | 我方组织真实承运车辆和承运司机，把商品车或配件作为货物送达；一期执行方式为板车运输 |
| 板车运输 | 整车运输服务的一种执行方式；板车装载商品车或配件，必须有真实板车和驾驶司机 |
| 开送服务 | 我方组织开送司机，直接驾驶厂商商品车到目的地；业务俗称开送或总驾 |
| 单车地跑 | 一辆商品车绑定一名开送司机单独执行 |
| 编组跑路 | 多辆商品车组成车队，逐车逐司机绑定，可记录领队和顺序 |
| 背载 | 母车承载子车共同执行，记录母子车、固定和装卸关系 |
| 自驾运输 | 开送服务的历史称呼，不作为新的一级服务类型 |
| 出人车/出车/出人 | 业务口语；在系统中用服务类型、执行方式和资源责任字段表达，不作为并列业务类型 |

## 三、核心业务对象

| 现状叫法 | 目标统一术语 | 定义 |
| --- | --- | --- |
| 第三方厂商、客户、厂家 | 委托厂商 | 向我方提出运输或开送需求并支付客户费用的企业 |
| 厂商导出表、原始表 | 厂商原始需求文件 | 从厂商后台原样导出的Excel或接口报文 |
| 每日统一Excel | 导入批次 | 某厂商、项目在某次导入中的原始文件和处理结果集合 |
| 表格一行、厂商计划 | 运输需求 | 委托厂商提出的一件货物或一辆商品车的交付要求 |
| 汽车、商品车、配件 | 交付标的/货物 | 需要被运输或需要完成开送交付的实物对象 |
| 被运的车 | 商品车 | 货物的一种；在开送服务中同时可能是实际行驶车辆 |
| 目标系统一货一单 | 业务订单 | 由运输需求生成，保存服务类型、执行方式、交付标的和结算主关联 |
| 厂商计划、发运计划 | 厂商发运计划 | 委托厂商提供的来源计划或批次指令 |
| 线路表、运输计划表 | 内部执行计划 | 我方对多个业务订单进行线路、途经点和时间编排的方案 |
| 整车调度单、派车单 | 运输任务 | 对一组业务订单进行派车和履约的可执行安排 |
| 车队、编组 | 执行编组 | 将多个开送执行单元组织在一起的可选对象 |
| 一辆承运车一趟、一个开送车次 | 执行单元 | 最小真实履约单元，保存本次司机、车辆/商品车、服务类型和交付标的关系 |
| 外车、板车、实际运输车 | 承运车辆 | 整车运输服务中实际装载货物并执行运输的车辆 |
| 开送司机、司机服务商 | 开送履约资源 | 开送服务中提供驾驶服务的司机或服务方 |
| 装车表、背车关系 | 实际装载/编组关系 | 板车装载、开送编组和母车子车之间的真实关系 |
| 收货回执、POD照片 | 签收凭证 | 收货方签字、盖章、照片或文件等原始证明 |
| 回单 | 电子回单 | 系统内关联业务订单、交付标的、签收凭证和审核结果的记录 |
| 整车运单费、厂商给的钱 | 客户应收 | 委托厂商应向我方支付的收入 |
| 包车费、板车费、司机服务费 | 履约应付 | 我方应向承运方或开送服务方支付的成本 |
| 支付码 | 客户付款码 | 厂商付款使用的渠道或识别标识，不等同于应收单 |
| 预付 | 履约预付款 | 服务开始前或约定节点支付的部分履约成本，比例按合同配置 |
| 尾款 | 履约尾款 | 送达、回单及审核条件满足后支付的剩余履约成本 |
| 推送财务的附件和金额 | 结算资料 | 结算中心生成并提交财务适配层的业务依据 |
| 结算单 | 结算中心单据 | 汇总费用明细、主体、付款码、审核和金蝶推送状态的业务单据 |

## 四、核心对象关系

```text
委托厂商
  → 导入批次
  → 运输需求
  → 业务订单（整车运输服务 / 开送服务）
  → 厂商发运计划
  → 内部执行计划
  → 运输任务
  → 执行编组（开送编组时可选）
  → 执行单元
  → 真实司机、承运车辆或商品车、承运方/司机服务方
  → 送达、电子回单和异常
  → 费用明细、客户应收、履约应付和结算单
  → 财务适配层 → 金蝶服务
```

不同服务下的执行单元：

| 服务类型/执行方式 | 执行单元表达 | 必须记录的关系 |
| --- | --- | --- |
| 整车运输服务/板车 | 1辆真实板车 + 1名承运司机 + 1-N件货物 | 板车、司机、承运方、实际装载清单和卸货顺序 |
| 开送服务/单车 | 1辆真实商品车 + 1名开送司机 | 商品车同时是交付标的和行驶车辆 |
| 开送服务/编组 | N个单车执行单元 + 1个执行编组 | 逐车逐司机、领队、顺序和统一线路 |
| 开送服务/背载 | 母车、子车和司机关联的执行单元 | 母子车、固定、装卸和对应业务订单 |

禁止以“虚拟货物”“虚拟车牌”“随便填的整车运单”替代上述真实关系。

| 业务专员/项目人员 | 是 | 导入需求、修正异常、维护项目和业务订单 |

| 回单人员 | 是 | 上传、审核、驳回和补传电子回单 |
| 签单结算员 | 是 | 核对客户应收、付款码和客户侧结算资料 |
| 外车/司机结算员 | 是 | 核对履约应付、预付款、尾款和成本资料 |
| 业务经理 | 是 | 审批改价、费用增补、异常和利润倒挂 |

| 前端组件 | 主要用户 | 主要用途 |

## 八、财务系统边界

待建运输系统与结算中心负责：

- 记录整车运输和开送服务的真实业务事实。
- 计算客户应收、履约应付、预付款、尾款和费用调整。
- 完成主体映射、业务审核、对账和结算资料生成。
- 关联付款码、回单、附件和金蝶推送状态。

金蝶服务负责接收财务适配后的单据或凭证，并承担既有的会计、发票、银行和实际收付款能力。两者通过财务适配层连接：

```text
运输运营系统 → 结算中心 → 财务适配层 → 金蝶服务
金蝶受理/入账/收付款结果 → 财务适配层 → 结算中心与业务状态
```

## 九、状态和权限原则

- 需求、业务订单、计划、任务、执行单元、交付标的、回单、异常、费用明细和结算单分别维护状态。
- 发车前必须通过资源和驻厂核验；结算前必须通过逐件送达、回单齐套、异常关闭、金额确认和主体资料校验。
- 调度和驻厂人员只能操作授权项目；价格、增补、利润倒挂、异常关闭和结算重推需要授权或审批。
- 金蝶实际受理、入账、收付款结果以适配层回写为准；运输系统不伪造财务完成状态。

## 十、禁止继续使用的模糊表述

| 不再单独使用 | 应改为 |
| --- | --- |
| 整车/板车/自驾三类并列业务 | 整车运输服务或开送服务；再写执行方式 |
| 车辆 | 商品车、承运车辆、板车、母车或子车 |
| 司机 | 承运司机或开送司机 |
| 运费 | 客户应收、履约应付、预付款、尾款或增补费用 |
| 运单 | 运输需求、业务订单、运输任务或执行单元；旧系统字段注明TMS映射 |
| 调度单 | 目标系统写运输任务；旧系统写TMS映射 |
| 回单 | 原始签收凭证或电子回单 |
| 已完成 | 交付标的已送达、回单已齐、任务已完成或结算已完成 |
| 虚拟车牌/虚拟货物 | 禁止；无正式车牌时记录VIN或临牌状态 |

如后续新增术语，必须先说明它与运输需求、厂商发运计划、内部执行计划、业务订单、运输任务和执行单元的关系，再进入产品、研发和测试文档。
