## 一、必须统一的五条规则

1. **厂商统一称为“委托厂商”**：指向我方提出运输需求并向我方支付费用的客户。
2. **两类车辆必须分开**：作为货物的汽车称为“被运输车辆”；实际装货运输的外车称为“承运车辆”。
3. **一件货物一条记录**：一条运输需求对应一件货物和一张内部运单，不再把几百件货物合成一张运单。
4. **一辆实车一次运输一张趟次单**：不再用一个虚拟车牌代表多辆实际承运车辆。
5. **收入和成本必须分开**：委托厂商应付我方的金额称为“客户应收运费”；我方应付实际承运方的金额称为“承运应付运费”。

## 三、核心对象关系

MVP阶段统一按以下关系设计：

```text
一个委托厂商
→ 提供多条运输需求

一条运输需求
= 一件货物
= 一张内部运单

多张内部运单
→ 可以组成一份运输计划

一份运输计划
→ 可以生成一至多张运输趟次单

一张运输趟次单
= 一辆真实承运车辆的一次运输
+ 一名当前司机
+ 一份实际装车清单
+ 一至多张内部运单

一张内部运单
→ 形成客户应收

一张运输趟次单
→ 形成承运应付
```

如果以后存在中转、接驳或分段运输，需要增加“运输分段”，不能直接改变以上对象含义。

| 财务审核员 | 在财务系统中审核、付款、记账和开票 |
| 业务经理 | 审批改价、费用调整、异常和结算 |

## 七、财务系统边界

待建运输系统负责：

- 记录运输业务事实。
- 计算业务应收和业务应付。
- 生成预付款、尾款和费用调整申请。
- 提供回单和运输依据。

财务系统负责：

- 财务审核。
- 实际收付款。
- 会计记账。
- 发票处理。
- 财务冲销。

两者通过财务适配层连接：

```text
运输业务系统
→ 财务适配层
→ 现有财务系统（优先复用）

未来更换财务系统时，只替换财务适配器，不改运输业务核心。
```

## 八、仍需业务确认的问题

1. 一条厂商原始记录是否始终只代表一件货物。
2. 一件货物是否存在拆分、中转、接驳或分段运输。
3. 换车后是修改原趟次，还是结束原趟次并创建新趟次。
4. 一张签收凭证是否可能覆盖多个货物。
5. 客户应收按内部运单、批次还是账期生成。
6. 承运应付是否始终按运输趟次生成。
7. 60%预付款比例是否固定，还是按合同配置。
8. 客户付款码与应收单、内部运单和实际收款之间的关系。
9. 业务主体、结算主体、收款主体、付款主体和开票主体是否一致。
10. 现有财务系统已经具备哪些接口和结算能力。

以上问题确认前，产品、研发和业务应继续使用本文统一术语，避免自行新增同义词。
