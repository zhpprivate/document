## 一、项目背景

公司承接多个委托厂商的汽车、商品车及大型配件交付业务。每个厂商每天可能下达数百条运输需求，但厂商后台、导出文件和字段格式各不相同。

目前主要依靠业务人员完成数据导出、Excel整理、计划编排、车辆和司机联系、运输跟踪、回单收集及TMS补录。现有TMS主要用于运输完成后的补单和结算：整车运输可能把多件货物合并成不准确的单据，开送服务则把人员服务伪装成货物运输，使用虚拟车牌和随意填写的运单金额。结果是系统单据与真实货物、商品车、车辆、司机和服务事实不一致，结算审核依赖线下核实。

MVP目标是建设内部运输运营与结算系统，直接记录真实业务事实，替代人工表格和事后假单补录，并通过财务适配层将审核后的结算结果推送到金蝶服务。

## 二、业务范围与分类

系统一级服务类型只有两类，不把“整车、板车、自驾”作为三个并列类型：

| 服务类型 | 业务口径 | 一期执行方式 | 核心履约事实 |
| --- | --- | --- | --- |
| 整车运输服务 | 我方提供承运车辆和承运司机，负责把商品车或配件作为货物运送到目的地；板车运输属于该服务 | 板车运输 | 真实承运车辆、真实司机、承运方、实际装载货物和线路 |
| 开送服务 | 我方提供开送司机，直接驾驶厂商提供的商品车到目的地；业务俗称开送或总驾 | 单车地跑、编组跑路、背载 | 真实开送司机、商品车VIN/车牌或临牌、逐车驾驶关系、编组或母子车关系 |

说明：

- “整车业务”是历史上位称呼；系统字段使用“整车运输服务”。
- “板车运输”是整车运输服务的一种执行方式，不是一级服务类型。
- “自驾运输”是开送服务的历史业务称呼；开送/总驾是服务标签，不再作为第三种一级类型。
- 两类服务共用需求接入、计划、任务、履约跟踪、回单、异常和结算主流程，但资源校验、执行关系和计价规则不同。

开送服务包括：

- 单车地跑：一辆商品车绑定一名开送司机单独送达。
- 编组跑路：多辆商品车组成车队，逐车绑定司机，可设置领队和编组顺序。
- 背载：母车承载子车共同运输，必须记录母子车、固定和装卸关系。

## 三、现状业务事实

1. 业务人员每天登录多个厂商后台，分一次或多次导出Excel，再按厂商和项目整理为当日增量需求表。
2. 不同项目字段可能不同；一行原则上代表一件货物，或一辆需要开送的商品车。
3. 厂商提供发运计划和逐件交付需求；我方业务人员据此形成内部执行计划，按线路、途经点、时间和运力人工合单。同一厂商或项目内可以合单，不同厂商原则上不交叉混装，专车专用。
4. 整车运输服务通常联系外部承运车辆、司机或派车公司；开送服务通常联系开送司机或司机服务方。两类服务都可能在执行开始前发生预付款，金额、比例和触发节点不固定。
5. 驻厂人员根据计划核对货物、商品车、车辆和人员，并办理保险、临牌等事项；发现问题后与厂商和项目人员沟通。
6. 运输过程主要通过电话、微信或短信人工跟踪。送达后逐货收集签收凭证，并按厂商要求回传厂商系统。
7. 当前流程在送达后补录TMS运单和调度单。开送服务因“人不是货物”，常使用虚拟货物、虚拟车牌和随意金额，仅为结算对账。
8. 调度结算对象通常为派车公司或司机服务方，实际付款账户可能是司机账户，发票可能由公司或平台提供。
9. 厂商支付可能带有支付码或其他灵活识别标识，付款码不等同于应收单，必须与应收、收款主体和实际到账关联。

## 四、原始需求数据

### 4.1 数据来源

- MVP以厂商后台人工导出Excel、业务人员批量导入为主。
- 系统预留厂商API接入能力，但不把厂商API接通作为一期验收条件。
- 每次导入必须保存原始文件、委托厂商、项目、导入批次、操作人和导入时间。

### 4.2 已知字段

| 字段组 | 已知字段示例 |
| --- | --- |
| 来源标识 | 委托厂商、项目、交货单号、厂商计划编号 |
| 业务分类 | 服务类型、运输方式、开送子类型（如适用） |
| 交付标的 | 名称、车型、规格、重量、底盘号/VIN、车牌或临牌（如有） |
| 发货信息 | 发货地、联系人、联系电话、计划发货时间 |
| 收货信息 | 经销商、收货地、省、市、联系人、联系电话、期望送达时间 |
| 路线价格 | 公里数、客户合同单价、客户应收运费 |
| 履约成本 | 承运车/司机或开送司机的成本、公里数、承运应付费用 |
| 结算标识 | 厂商付款码、合同号、结算批次及其他厂商识别字段 |

厂商真实模板、字段必填性、唯一键、变更与取消规则尚未完整取得，必须通过可配置字段映射处理，不能在程序中写死。

## 五、MVP目标业务流程

```text
厂商后台导出Excel
→ 原始文件与导入批次留存
→ 字段映射、校验、去重和人工纠错
→ 生成运输需求与业务订单，并选择整车运输服务或开送服务
→ 人工编制运输计划并试算客户价、履约成本和毛利
→ 生成运输任务及1-N个执行单元
→ 整车服务绑定真实承运车、司机、承运方和装载清单
→ 开送服务绑定真实开送司机、商品车及单车/编组/背载关系
→ 驻厂核验并确认发车，按配置触发预付款申请
→ 内部人员人工登记运输节点、异常和逐货送达
→ 上传、审核电子回单；不使用虚拟运单或虚拟车牌
→ 结算中心生成客户应收、履约应付、付款申请和结算资料
→ 结算审核通过后，经财务适配层推送金蝶服务
→ 接收金蝶受理、入账、收付款结果并回写业务状态
```

## 六、核心对象与关系

```text
委托厂商
  → 导入批次
  → 运输需求（厂商的一条原始交付要求）
  → 业务订单（服务类型、交付标的和结算主关联）
  → 厂商发运计划（来源计划）
  → 内部执行计划（线路、途经点和时间编排）
  → 运输任务（一次可执行的业务安排）
  → 执行编组（开送编组时可选）
  → 执行单元（一次真实车辆运输或一次真实开送服务）
  → 送达、电子回单和异常
  → 费用明细、客户应收、履约应付和结算单
  → 金蝶服务单据及结果
```

“内部运单”是现有TMS历史叫法。MVP不再为了结算补录虚拟内部运单；如需兼容旧系统，仅作为旧系统映射字段保存，不能替代业务订单、执行单元或真实履约记录。

## 七、核心业务规则

| 编号 | 规则 |
| --- | --- |
| R-01 | 系统一级服务类型只能是“整车运输服务”和“开送服务”；执行方式由服务类型约束。 |
| R-02 | 每条运输需求必须保留原始来源、交付标的、服务类型和业务订单，不得把多件货物合并后丢失逐件明细。 |
| R-03 | 整车运输服务的每个执行单元必须绑定真实承运车辆、真实司机、承运方和实际装载清单；板车司机不能省略。 |
| R-04 | 开送服务的每个执行单元必须绑定真实开送司机和真实商品车；商品车可同时是交付标的和行驶车辆，不要求虚构承运车辆。 |
| R-05 | 开送服务必须记录单车、编组或背载关系；商品车使用真实VIN、车牌或临牌，缺少正式车牌时允许为空但不得填虚拟车牌。 |
| R-06 | 车辆角色（承运车、板车、商品车、母车、子车）是执行记录属性，不永久固化在车辆档案中。 |
| R-07 | 厂商发运计划进入计划池后，可形成一份内部执行计划；内部执行计划可包含多个业务订单，一个运输任务可拆分为多个执行单元，但单个执行单元不得混合两种服务类型。 |
| R-08 | 每件交付标的分别登记送达结果和电子回单；一份凭证可关联多件，但必须保留逐件核销结果。 |
| R-09 | 客户应收与履约应付分开建模。正常业务下客户应收应高于履约成本；倒挂、负毛利或费用异常时必须提示并审批。 |
| R-10 | 客户合同价、履约成本、途中增补、扣款和理赔必须保留计算依据、金额、调整原因和审批记录。 |
| R-11 | 预付款比例、尾款比例和付款节点按项目或合同配置；整车服务和开送服务可配置不同触发条件。 |
| R-12 | 回单未齐、关键异常未关闭、金额未确认或主体资料不完整时，不得生成可支付的尾款资料。 |
| R-13 | 厂商付款码只是渠道或识别标识，必须关联客户应收、结算单、收款主体和实际到账结果。 |
| R-14 | 结算中心必须以业务订单、执行单元和费用明细为业务依据，不得以车牌作为唯一主键，不得生成虚拟运单或虚拟调度单。 |
| R-15 | 结算推送必须具备幂等号、版本号、失败重试、驳回修改、结果回写和审计记录。 |
| R-16 | 导入、分类、改价、换车换人、异常关闭、回单审核、结算审核和金蝶推送等关键操作必须留痕。 |

## 八、MVP功能范围

### 8.1 数据导入与需求

- Excel批量导入、原文件留存和导入批次管理。
- 按厂商/项目配置字段映射、必填校验、唯一键和增量规则。
- 重复识别、错误提示、人工修正及重新处理。
- 运输需求、业务订单和真实交付标的查询、变更、取消及状态追踪。

### 8.2 计划、价格与派车

- 待计划池、人工合单、线路和途经点编排。
- 选择整车运输服务或开送服务；开送服务选择单车、编组或背载。
- 客户合同价与履约成本试算，支持人工调整、增补和审批。
- 运输任务、执行单元、开送执行编组和实际装载关系。
- 整车服务绑定真实承运车、司机、承运方；开送服务绑定真实商品车和开送司机。

### 8.3 履约、回单与异常

- 驻厂核验、保险/临牌准备、发车、到达、签收等节点登记。
- 电话、微信、短信反馈由内部人员人工代录；不建设司机端或自动消息解析。
- 异常登记、责任人、处理记录、理赔支出和关闭状态。
- 逐件电子回单上传、审核、驳回、补传和齐套检查。

### 8.4 结算中心与金蝶适配

- 结算中心生成客户应收、履约应付、预付款、尾款、增补、扣款和理赔费用明细。
- 按业务订单和执行单元核对收入、成本、毛利及付款码关联。
- 财务审核、对账、开票、收付款所需资料和主体映射。
- 通过财务适配层向金蝶服务推送审核后的结算单据或凭证，并回写受理、入账、付款和失败结果。
- 结算重试、幂等、驳回、重推和全链路审计。

### 8.5 公共能力

- 项目、合同、委托厂商、履约主体、结算主体、收款人、付款主体、开票方、司机、车辆和价格规则等基础资料。
- 用户、角色、数据权限、审批、操作日志、文件影像和基础报表。
- 状态机和业务门禁，避免跳过核验、回单或审批直接结算。

## 九、第一期明确不建设

- 司机APP、司机H5、司机小程序。
- 承运商门户和委托厂商门户。
- 持续定位、自动偏航检测和自动超时预警。
- 自动发送微信或短信并自动解析回复。
- 全局智能合单、自动派车和无人审批。
- 所有厂商API的实际接通；Excel仍为一期主入口，API只预留扩展点。
- 把金蝶财务能力整体重做；一期建设结算中心和金蝶服务适配，不替换金蝶总账、发票、银行等既有财务能力。

以上能力可预留接口，但不得成为MVP上线的前置条件。

## 十、系统边界

待建系统负责记录真实运输和开送服务事实、过程状态、回单、费用计算依据、结算中心单据和推送状态。

结算中心负责业务应收应付、费用审核、主体映射、付款申请和结算状态；金蝶服务负责接收财务适配后的单据或凭证，并返回受理、入账、开票、收付款等结果。金蝶内部财务能力不在运输系统内重做。

```text
运输运营系统 → 结算中心 → 财务适配层 → 金蝶服务
      ↑             ↓                  ↓
 真实履约事实   审核/对账/付款资料     受理、入账、收付款结果
```

## 十一、MVP完成判定

1. 一批Excel需求可以被导入、校验并形成逐件运输需求和业务订单。
2. 同一套流程可以分别完成整车运输服务和开送服务；两类服务的真实资源校验和执行关系不同但不互相伪装。
3. 整车执行单元均有真实承运车辆、司机和装载清单；开送执行单元均有真实商品车和开送司机，不出现虚拟车牌或假运单。
4. 可以逐件跟踪送达、处理异常并审核电子回单。
5. 结算中心可以分别核算客户应收、履约应付、付款码、毛利和增补费用。
6. 结算审核通过后，可以幂等推送金蝶服务并回写处理结果，不再依赖线下把业务事实改成“对得上”的金额。

## 十二、详细设计前必须确认

1. 各厂商/项目真实Excel样表、字段说明、唯一键、增量、变更和取消规则。
2. 不同厂商、项目、批次和日期之间允许合单的准确边界。
3. 整车运输服务中承运车、板车司机、承运方和事故责任的主体关系。
4. 开送服务中司机服务方、商品车车牌/临牌、编组换驾和背载数量规则。
5. 客户合同价、履约成本、增补费用、预付/尾款节点和不同服务的计价规则。
6. 客户应收、履约应付、费用明细的生成粒度，以及多货、多执行单元的成本和毛利分摊。
7. 回单是一货一份还是允许一份覆盖多货，以及厂商回传方式。
8. 保险、临牌、油费、路桥费、事故和货损的承担及理赔流程。
9. 结算主体、合同相对方、履约方、收款人、付款主体和开票方的关系。
10. 金蝶服务可接收的单据类型、字段、状态、幂等规则、失败重试和结果回写方式。

## 十三、上线前确认

- 厂商API是否在某个项目启用，以及启用项目的验收范围。
- 自动定位、自动消息、智能合单、门户和司机端的后续立项时间。
- 经营报表、备份恢复、附件保存期限和长期审计要求。
