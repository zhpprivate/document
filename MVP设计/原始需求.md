# 运输管理系统原始需求（MVP最终基线）

| 文档属性 | 内容 |
| --- | --- |
| 版本 | V1.0 |
| 日期 | 2026年8月24日 |
| 用途 | 作为MVP产品设计、研发拆分和业务评审的统一需求输入 |
| 口径 | 已确认事实直接写入；尚未明确的内容统一列入“待确认事项” |

## 一、项目背景

公司承接多个委托厂商的汽车、商品车及大型配件运输业务。每个厂商每天可能下达数百条运输需求，但厂商后台、导出文件和字段格式各不相同。

目前主要依靠业务人员完成数据导出、Excel整理、计划编排、车辆和司机联系、运输跟踪、回单收集及TMS补录。现有TMS更多用于运输完成后的补单和结算，系统单据与真实货物、车辆、司机之间经常不能一一对应，导致过程不可追踪、结算审核依赖线下确认。

MVP目标是建设内部使用的运输运营系统，替代上述人工表格和TMS补录环节，同时尽量复用现有结算、财务和金蝶链路。

## 二、业务范围

系统一级业务类型统一为三类：

| 业务类型 | 通俗口径 | 执行含义 |
| --- | --- | --- |
| 整车业务 | 出人车 | 我方组织承运车辆和司机，完成货物取送 |
| 板车运输 | 出车 | 使用专用板车装载商品车或大型配件运输 |
| 自驾运输 | 出人 | 我方组织司机，直接驾驶厂商商品车到目的地 |

自驾运输包括：

- 单车地跑：一辆商品车绑定一名司机单独送达。
- 编组跑路：多辆商品车组成车队，逐车绑定司机，可设置领队。
- 背载：母车承载子车共同运输，必须记录母子车关系。

“开送业务、总驾服务”统一作为自驾运输的业务称谓，不作为第四种一级业务类型。

## 三、现状业务事实

1. 业务人员每天登录多个厂商后台，分一次或多次导出Excel，再按项目整理为当日增量需求表。
2. 不同项目字段可能不同；一行原则上代表一件货物或一辆需要运输的商品车。
3. 业务人员根据线路、途经点、时间和运力人工形成运输计划。同一厂商或项目内可以合单，不同厂商原则上不交叉混装，专车专用。
4. 业务人员联系外部车辆、司机或承运方，并支付运输预付款；预付款金额或比例目前不固定。
5. 驻厂人员根据计划核对货物、车辆和人员，并办理保险、临牌等事项；发现问题后与厂商和项目人员沟通。
6. 运输过程主要通过电话、微信或短信人工跟踪。货物送达后，逐货收集签收凭证，并按厂商要求回传厂商系统。
7. 运输完成后，业务人员在现有TMS补录整车运单和调度单，推进至已送达并触发结算。
8. 现有TMS可能将多件货物合并为一张整车运单，也可能用一个非真实车牌代表多辆实际车辆，导致财务必须线下核实。
9. 调度结算对象通常为派车公司，实际付款账户可能是司机账户，发票可能由公司或平台提供。
10. 现有结算链路大致为：运输业务资料 → 现有结算系统审核/对账 → 开票/收付款 → 金蝶。

## 四、原始需求数据

### 4.1 数据来源

- MVP以厂商后台人工导出Excel、业务人员批量导入为主。
- 系统预留厂商API接入能力，但不把所有厂商API接通作为一期完成条件。
- 每次导入必须保存原始文件、厂商、项目、导入批次、操作人和导入时间。

### 4.2 已知字段

| 字段组 | 已知字段示例 |
| --- | --- |
| 来源标识 | 委托厂商、项目、交货单号、厂商计划编号 |
| 货物信息 | 名称、车型、规格、重量、底盘号/VIN、运输方式 |
| 发货信息 | 发货地、联系人、联系电话、计划发货时间 |
| 收货信息 | 经销商、收货地、省、市、联系人、联系电话、期望送达时间 |
| 路线价格 | 公里数、客户结算单价、客户应收运费 |
| 外部运力价格 | 外车单价、外车公里数、承运应付运费 |

厂商真实模板、字段必填性、唯一键、变更与取消规则尚未完整取得，必须通过可配置字段映射处理，不能在程序中写死。

## 五、MVP目标业务流程

```text
厂商后台导出Excel
→ 原始文件与导入批次留存
→ 字段映射、校验、去重和人工纠错
→ 一条运输需求生成一张内部运单
→ 人工编制运输计划并试算价格
→ 生成运输任务及1-N个执行单元
→ 绑定司机、车辆、承运方及装载/编组关系
→ 驻厂核验并确认发车
→ 内部人员人工登记运输节点和异常
→ 逐货上传、审核电子回单
→ 生成客户应收、承运应付及结算资料
→ 推送现有结算系统并回写处理状态
```

## 六、核心业务规则

| 编号 | 规则 |
| --- | --- |
| R-01 | 一条运输需求对应一件货物，并生成一张内部运单；不得为了省事合并后丢失货物明细。 |
| R-02 | 一份运输计划可以包含多张内部运单，并可拆成一个或多个运输任务。 |
| R-03 | 一个运输任务可以包含一个或多个执行单元；编组只在需要时建立。 |
| R-04 | 每个执行单元必须保存真实司机、车辆、承运方和货物关系，不得使用虚拟车牌代替多辆实车。 |
| R-05 | 车辆的“承运车、板车、自驾车、母车、子车”是本次执行角色，不永久固化在车辆档案中。 |
| R-06 | 每件货物分别登记送达结果和电子回单；允许一份凭证关联多件货物，但必须保留逐货核销结果。 |
| R-07 | 客户应收与承运应付分开建模。正常业务下客户应收应大于承运成本；倒挂时必须提示并审批。 |
| R-08 | 客户价格、承运价格及途中增补费用必须保留计算依据、调整原因和审批记录。 |
| R-09 | 预付款比例、尾款比例和付款节点按项目或合同配置，不固定为60%和40%。 |
| R-10 | 回单未齐、关键异常未关闭或金额未确认时，不得生成可结算的尾款资料。 |
| R-11 | 厂商付款码只是收款渠道或识别标识，必须与客户应收和实际收款结果建立关联。 |
| R-12 | 导入、改价、换车换人、异常关闭、回单审核和结算推送等关键操作必须留痕。 |

## 七、MVP功能范围

### 7.1 数据导入与需求

- Excel批量导入、原文件留存和导入批次管理。
- 按厂商/项目配置字段映射、必填校验和唯一键。
- 重复识别、错误提示、人工修正及重新处理。
- 运输需求和内部运单查询、变更、取消及状态追踪。

### 7.2 计划、价格与派车

- 待计划池、人工合单、线路和途经点编排。
- 三类业务及自驾子类型选择。
- 客户价格与承运价格试算、人工调整和审批。
- 运输任务、执行单元、可选执行编组。
- 司机、车辆、承运方档案和派车绑定。
- 板车装载、自驾编组、背载母子车关系。

### 7.3 履约、回单与异常

- 驻厂核验、发车、到达、签收等节点登记。
- 电话、微信、短信反馈的人工代录。
- 异常登记、责任人、处理记录和关闭状态。
- 逐货电子回单上传、审核、驳回、补传和齐套检查。

### 7.4 结算资料

- 客户应收、承运应付、预付款、尾款和增补扣款明细。
- 业务收入、运输成本和毛利检查。
- 按现有结算系统要求生成并推送结算资料。
- 回写审核、对账、开票、付款或驳回状态。

### 7.5 公共能力

- 项目、合同、客户、承运方、司机、车辆、价格规则等基础资料。
- 用户、角色、数据权限、审批、操作日志、文件影像和基础报表。
- 状态机和业务门禁，避免跳过核验、回单或审批直接结算。

## 八、第一期明确不建设

- 司机APP、司机H5、司机小程序。
- 承运商门户和委托厂商门户。
- 持续定位、自动偏航检测和自动超时预警。
- 自动发送微信或短信并自动解析回复。
- 全局智能合单、自动派车和无人审批。
- 全面替换现有结算系统或直接重做金蝶财务能力。

以上能力可预留接口，但不得成为MVP上线的前置条件。

## 九、系统边界

待建运输系统负责记录真实运输业务事实、过程状态、回单、应收应付计算依据及结算资料。

现有结算/财务系统继续负责财务审核、对账、开票、实际收付款、会计记账和金蝶处理。两者通过结算适配组件隔离，未来更换财务系统时不修改运输业务核心模型。

## 十、MVP完成判定

满足以下条件即可认为MVP主链路完成：

1. 一批Excel需求可以被导入、校验并形成逐货内部运单。
2. 三类业务都可以形成运输任务、真实执行单元和资源绑定关系。
3. 可以逐货跟踪送达、处理异常并审核电子回单。
4. 可以分别核算客户应收、承运应付和毛利，不再依赖虚拟运单或虚拟车牌做账。
5. 可以向现有结算系统提交完整、可追溯的结算资料并回写状态。

## 十一、上线前必须确认

1. 各厂商/项目的真实Excel样表、字段说明、唯一键、增量、变更和取消规则。
2. 不同厂商、项目、批次和日期之间允许合单的准确边界。
3. 三类业务分别需要的车辆、司机、承运方及责任主体。
4. 编组途中换驾、背载数量和母子关系变更规则。
5. 客户价格、承运价格、增补费用、预付和尾款的计算及审批规则。
6. 回单是一货一份还是允许一份覆盖多货，以及厂商回传方式。
7. 保险、临牌、油费、路桥费、事故和货损的承担及理赔流程。
8. 现有结算系统的名称、接口、字段、状态、失败重试和对账方式。
9. 客户付款码与应收单、收款主体和实际到账之间的对应关系。
10. 业务主体、合同主体、结算主体、开票主体和实际收付款主体的关系。
